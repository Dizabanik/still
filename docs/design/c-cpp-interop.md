# C and C++ interoperability proposal

Status: proposal for review, not an implemented feature. The syntax and command
lines below describe the intended interface. This proposal does not change
Whisky's type-first declarations or make foreign code memory-safe.

## What exists today

Whisky can declare and call external C symbols with declarations such as
`extern "c" fn f64 sqrt(f64 value);`. `stdc` also declares selected C library
functions. The driver links a single generated object with Clang.

This is not yet a complete foreign-language interface:

- Headers are not imported. Signatures must be declared manually or supplied by
  the built-in library surface.
- The driver has no general library/object inputs, include-path configuration,
  C++ link mode, generated headers, or library packaging. Its current `-c` writes
  fixed-name LLVM artifacts rather than behaving like a conventional C compiler.
- LLVM types are constructed directly. That alone does not prove correct C
  aggregate calling conventions on every supported target.
- External declarations reject managed Whisky representations. External calls
  currently receive `nounwind`; arbitrary C++ calls cannot inherit that claim.

Relevant implementation: `src/main.c`, `src/driver_imports.c`,
`src/codegen/codegen_compile.c`, and `src/codegen/codegen_func.c`.

## Intended experience

Import a header and use its declarations without maintaining a second signature
list. Keep the foreign API in an explicit namespace.

```c
/* geometry.h */
typedef struct Point {
    double x;
    double y;
} Point;

double point_length(const Point *point);
```

```wky
// Proposed syntax, not supported yet.
import c "geometry.h" as C;

fn f64 measure() {
    C.Point point = {x: 3.0, y: 4.0};
    return C.point_length(&point);
}
```

Calling an unverified pointer-taking function requires a foreign/unsafe context
or a checked binding contract. This example shows name and type mapping; it
does not establish such a contract. Importing a header does not establish that
the function keeps no pointers or obeys their bounds.

For C++, import the existing header and retain its namespaces, classes, methods,
and overloads:

```cpp
// geometry.hpp
namespace geometry {
class Vec2 {
public:
    Vec2(double x, double y) noexcept;
    double length() const noexcept;
private:
    double x_;
    double y_;
};
}
```

```wky
// Proposed syntax, not supported yet.
import cpp "geometry.hpp" as cpp;

fn f64 measure() {
    cpp.geometry.Vec2 point = cpp.geometry.Vec2(3.0, 4.0);
    return point.length();
}
```

The imported class keeps its C++ representation. Construction, copying, moving,
and destruction follow its actual C++ rules; an automatic object receives its
destructor at scope exit. No heap allocation is required simply to cross a
language boundary. A later template import could allow
`cpp.std.vector<i32> values;`, with Clang selecting and instantiating the real C++
specialization. Its iterator and element invalidation rules still apply.

Export Whisky functions explicitly:

```wky
// math.wky; proposed export syntax.
export "c" fn i32 wky_math_add(i32 a, i32 b) {
    return a + b;
}
```

```c
/* C caller; header generated by still. */
#include "math.h"

int main(void) {
    return wky_math_add(20, 22) == 42 ? 0 : 1;
}
```

The same header must be valid in C++ and wrap declarations in `extern "C"`.
A generated C++ convenience header can additionally expose names such as
`wky::math::add(20, 22)` and RAII classes for explicit opaque-handle APIs.
Whisky's managed `owner<T>` and `ref<T>` layouts are not exported as raw C/C++
structs. Foreign code uses declared operations on opaque handles, or an explicit
borrowed-buffer interface with length and retention contracts.

Tentative build commands:

```sh
still -c math.wky -o build-cmake/math.o \
  --emit-c-header build-cmake/math.h \
  --emit-cpp-header build-cmake/math.hpp
clang++ main.cpp build-cmake/math.o -Ibuild-cmake -o build-cmake/app
```

The driver will also accept C/C++ sources, existing objects, archives, `-I`,
`-D`, `-L`, and `-l`, and offer static/shared library output. Required system and
Whisky runtime link inputs must be supplied through generated build metadata or
a CMake target. The simple command above illustrates an export that needs no
managed runtime. Conventional object output requires migrating current `-c`
users and providing explicit bitcode/IR output options.

## Implementation sequence

1. **Library foundation and bidirectional C.** Implement explicit exported
   symbols, object/static/shared library builds without an application `main`,
   generated C headers, linker inputs, callbacks, and separate compilation.
   Start with integers, floats, raw pointers, enums, and verified C records.
   Define runtime initialization/finalization, symbol visibility, and a single
   program-wide managed runtime. Independent Whisky objects must not silently
   create incompatible allocation registries. Reject unsupported signatures
   rather than emitting plausible but incorrect prototypes.

2. **Header import through Clang.** Use Clang's preprocessor, AST, semantic
   analysis, record layouts, and code generation. The compiler can remain C;
   a small C++ component exposes a C interface to these facilities. A libclang
   name extractor alone is insufficient for C++ overload resolution and template
   instantiation. Reuse the target triple, defines, include paths, language mode,
   packing flags, and ABI settings used to build the foreign library. Cache
   header state with dependency and option invalidation. Import constants where
   meaningful; diagnose unsupported macros explicitly.

3. **C++ objects and templates in both directions.** Add namespaces, overloads,
   references, const qualification, constructors/destructors, deleted copy/move
   operations, and template instantiation through Clang. Use Clang-generated
   adapters initially, linked as LLVM IR when optimization permits. Then emit
   direct ABI calls where validated. Imported C++ records retain their exact
   layout and access rules. Generate C++ facades for exported Whisky APIs;
   materialize requested generic specializations rather than pretending a
   precompiled Whisky generic is already a C++ template. Inheritance, virtual
   dispatch, RTTI, and advanced template APIs need explicit later coverage.

These stages provide useful two-way integration early while keeping the final
goal broader than a manually maintained collection of C wrappers.

## Safety and errors at the boundary

- Scalars and plain records can cross by value without marshaling or allocation.
  Strings, slices, and buffers need explicit encoding, length, ownership, and
  retention rules. A C string is not automatically a Whisky `str`.
- Foreign raw pointers and references remain foreign. They cannot silently
  become checked `ref<T>` values. A C++ owner or RAII destructor alone cannot
  prove that a retained pointer stays valid after mutation or reallocation.
- Checked adapters can cover APIs with known lifetime/effect contracts. Unknown
  foreign effects remain unverified. Bounds, retention, thread-safety, allocator
  compatibility, and invalidation must not be inferred from a header alone.
- Destruction uses the original allocator and destructor. `free`, `delete`, and
  Whisky owner cleanup are not interchangeable.
- C++ exceptions must not unwind through Whisky frames. Proven `noexcept` calls
  can use the direct path. Potentially throwing calls need generated adapters
  that catch and translate exceptions into a documented status/error value,
  suitable for Whisky's error handling. Callbacks need the same rule in reverse.
- Exported Whisky failures must have an explicit error-result or trap policy;
  a C/C++ caller must never receive an undocumented representation or unwinding
  behavior. Foreign code can still contain undefined behavior.

## Performance requirements and verification

Clang supplies C/C++ ABI lowering, including aggregate coercion, alignment,
hidden return pointers, and mangled names. Match compiler/standard-library ABI
settings before accepting a foreign object; a shared LLVM backend alone is not
an ABI guarantee. Clang is a build-time dependency, not a runtime parser.

Prefer direct calls and stack-resident values. Use LLVM optimization and optional
LTO to remove eligible adapters. Do not promise that every adapter disappears or
that every boundary has zero cost; inspect emitted code and measure it. Cache
header analysis, and report cold and warm import times separately.

Tests must compile real C/C++ callers and callees, then compare independent
expected results in both directions at O0/O2/O3 on Linux x86-64 and macOS ARM64.
Cover mixed-width scalars, booleans, floats, structs by value and return, packing,
callbacks, varargs promotions, multiple modules, and runtime lifecycle. C++ cases
must include overloads, templates, copy/move/destructor counts, exception
translation, and invalidated views. Negative tests cover incompatible target/ABI
settings and forbidden managed-layout exports. Sanitizers check applicable
foreign implementations.

Benchmarks should compare equivalent pure-C++ and mixed-language programs with
runtime inputs: ordinary and inlineable calls, callbacks, records, object
lifetimes, and bulk buffer operations. Use separate compile/import measurements,
balanced repeated runs, and independent output oracles. Include adapter counts,
allocations, and emitted IR/assembly alongside timing results.
